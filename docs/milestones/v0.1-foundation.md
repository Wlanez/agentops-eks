# v0.1 Foundation

## Objective

Build the smallest professional foundation that proves we can provision Amazon EKS from code, package a real service, deploy it with Helm, and deliver it through GitHub Actions.

The milestone is intentionally **not AI yet**. Its job is to create a reliable substrate that later agent/observability work can trust.

## Architecture target

```text
Developer / GitHub
       │
       ├── Terraform ───────────────┐
       │                            │
       │                       AWS account
       │                            │
       │                 ┌──────────┴──────────┐
       │                 │                     │
       │                VPC                   ECR
       │                 │                     ▲
       │          ┌──────┴──────┐              │
       │          │             │              │
       │       public        private           │
       │       subnets       subnets            │
       │          │             │               │
       │      NAT/LB path   EKS managed nodes  │
       │                        │               │
       └─ GitHub Actions ───────┼───────────────┘
                                │
                              Helm
                                │
                          FastAPI demo app
```

For the lab profile, one NAT gateway may be used to control cost; document that this is not a highly available production topology. The Terraform design should make it possible to evolve networking later without rewriting the entire repo.

## Prerequisites

### Accounts

- AWS account with appropriate IAM permissions.
- GitHub Actions enabled for the repository.

### Local tools

- Git
- Docker-compatible runtime
- AWS CLI v2
- `kubectl`
- Terraform
- Helm 3
- Python 3.x

Verification commands should be documented, for example:

```bash
aws --version
kubectl version --client
terraform version
helm version
docker version
python --version
```

### Local AWS identity

The developer must be able to run:

```bash
aws sts get-caller-identity
```

and identify the account/role being used before provisioning infrastructure.

## Workstream 1 — Terraform bootstrap

### Required

- Terraform and AWS provider constraints.
- S3-backed remote Terraform state before final v0.1 completion.
- State protection/locking using a supported backend mechanism.
- Environment variables/input variables for region, environment and resource naming.
- Consistent tags, including project and environment.

### Validation

```bash
terraform fmt -check
terraform init
terraform validate
terraform plan
```

### Done when

A new developer can identify where state lives, initialize Terraform and generate a plan without editing hard-coded account values throughout the project.

## Workstream 2 — Networking

### Required

- VPC.
- At least two Availability Zones.
- Public and private subnet separation in the reference architecture.
- Route tables and Internet/NAT routing required by the chosen lab topology.
- Security groups created by Terraform.
- No inbound SSH dependency for cluster administration.

### Lab cost decision

Default v0.1 may use one NAT gateway to reduce lab cost. The documentation must state the availability tradeoff and identify NAT as a cost driver.

### Done when

Terraform creates networking reproducibly and EKS worker nodes have the egress/connectivity required to join and pull images without manual console fixes.

## Workstream 3 — Amazon EKS

### Required

- EKS control plane.
- A Kubernetes version supported by AWS at implementation time, exposed as a pinned/configured variable rather than assumed forever.
- Linux EC2 managed node group.
- Small lab-sized node configuration exposed through variables.
- EKS access configured for the developer/admin identity.
- Core EKS add-ons required by the cluster explicitly managed/documented.

### Validation

```bash
aws eks update-kubeconfig --name <cluster> --region <region>
kubectl get nodes
kubectl get pods -A
```

### Done when

All expected nodes are `Ready`, system pods are healthy and access can be recreated from documented commands.

## Workstream 4 — Amazon ECR

### Required

- ECR repository managed by Terraform.
- Image scan-on-push or equivalent baseline scanning enabled where supported/configured.
- Lifecycle policy or documented cleanup strategy for old lab images.
- CI receives only the permissions it needs to authenticate and push/pull required artifacts.

### Tagging standard

Deploy immutable tags such as:

```text
<git-commit-sha>
```

Optionally add human-friendly tags for navigation, but do not use mutable `latest` as the release identity.

### Done when

A locally or CI-built image can be pushed to ECR and traced back to a source commit.

## Workstream 5 — Demo FastAPI service

The demo application should be deliberately small. Its purpose is to give the platform something realistic to deploy, observe and later break on purpose.

### Required endpoints

- `GET /healthz` — process is alive.
- `GET /readyz` — application is ready to receive traffic.
- `GET /version` — returns build/release identity.
- One simple business endpoint such as `GET /api/orders/{id}` or `GET /api/status` that can later be instrumented and subjected to failure scenarios.

### Required engineering baseline

- Automated unit tests.
- Structured application logs where practical.
- Graceful process startup/shutdown.
- Configuration from environment variables.
- No embedded AWS credentials/secrets.

### Container requirements

- Multi-stage build if it meaningfully reduces image/runtime complexity.
- Non-root runtime user.
- Deterministic dependency installation.
- Health behavior compatible with Kubernetes probes.

### Done when

The service passes tests locally, builds into a container and returns healthy endpoints when run from that image.

## Workstream 6 — Helm deployment

### Required chart resources

- Namespace strategy documented.
- Deployment.
- ClusterIP Service.
- Config via values/environment variables.
- Liveness probe.
- Readiness probe.
- CPU/memory requests.
- CPU/memory limits.
- Rolling update settings.
- Image repository and immutable tag provided through values.

### Deliberately out of scope for v0.1

- Full ingress architecture unless needed for the chosen demo flow.
- Service mesh.
- Autoscaling.
- AI agent.
- OpenTelemetry stack.

For demos, `kubectl port-forward` is acceptable in v0.1. External ingress can be introduced when it serves a real requirement.

### Validation

```bash
helm lint helm/demo-api
helm upgrade --install demo-api helm/demo-api \
  --namespace agentops-demo --create-namespace \
  --set image.tag=<commit-sha>

kubectl rollout status deployment/demo-api -n agentops-demo
kubectl get pods -n agentops-demo
```

### Done when

A fresh Helm install creates a healthy deployment without manually editing Kubernetes resources in the cluster.

## Workstream 7 — GitHub Actions CI

### Pull request / CI workflow

Required checks:

1. Python lint/static checks as selected by the project.
2. Unit tests.
3. Terraform formatting and validation.
4. Helm lint.
5. Container build test.

A failing check must prevent treating the commit as releasable.

## Workstream 8 — GitHub Actions CD

### Authentication requirement

Use GitHub OIDC federation to AWS. Do not store long-lived AWS access key IDs and secret access keys in GitHub Actions secrets.

### Deployment path

```text
merge/release trigger
      ↓
tests/checks
      ↓
build container
      ↓
immutable tag = commit SHA
      ↓
push ECR
      ↓
configure EKS access
      ↓
helm upgrade --install
      ↓
rollout status
      ↓
smoke test
```

### Required CI/CD safeguards

- Explicit GitHub workflow permissions.
- AWS IAM role trust restricted to the intended repository/branch/environment pattern.
- Deployment role is not AWS administrator/root.
- Fail if rollout or smoke test fails.
- Output deployed commit/image identity in the workflow summary/log.

### Done when

A merge/release event can deploy the application without a developer manually pushing an image or running Helm from a laptop.

## Workstream 9 — Smoke test

The pipeline should verify more than “Kubernetes accepted the manifest.”

Minimum proof:

- Deployment rollout succeeded.
- Ready replicas match expected replicas.
- Health/readiness endpoint returns success.
- `/version` reports the commit/image release that the workflow intended to deploy.

## Workstream 10 — Documentation and portfolio evidence

By the end of v0.1 include:

- Architecture diagram.
- Setup prerequisites.
- Provision commands.
- Deployment workflow explanation.
- Screenshots or terminal evidence of healthy EKS nodes/pods and successful GitHub Actions deployment.
- Key design decisions and tradeoffs.
- Teardown instructions.
- Cost-driver notes.

The README should answer in under two minutes:

1. What does this project demonstrate?
2. How is it deployed?
3. What is production-style about the foundation?
4. What comes in v0.2?

## Suggested implementation order

1. Bootstrap Terraform state.
2. Create VPC/networking.
3. Create EKS + managed node group.
4. Verify `kubectl` access.
5. Create ECR.
6. Build/test demo FastAPI application locally.
7. Containerize and push one image manually once to prove the path.
8. Create Helm chart and deploy manually once.
9. Add GitHub Actions CI.
10. Configure GitHub OIDC → AWS.
11. Add automated build/push/deploy workflow.
12. Add smoke test.
13. Run clean destroy/recreate verification.
14. Capture evidence and tag `v0.1.0`.

Manual verification is allowed while building the milestone; the final Definition of Done requires the documented automated path.

## Definition of Done — v0.1.0

All must be true:

- [ ] `terraform fmt -check` and `terraform validate` pass.
- [ ] Infrastructure can be provisioned from Terraform without console-only required steps.
- [ ] Remote state is configured.
- [ ] EKS managed nodes become `Ready`.
- [ ] ECR exists and accepts the CI image.
- [ ] Demo API has automated tests.
- [ ] Container runs as the intended non-root runtime identity.
- [ ] Helm lint passes.
- [ ] Deployment has readiness/liveness probes and resource requests/limits.
- [ ] GitHub Actions authenticates to AWS using OIDC.
- [ ] GitHub Actions builds and pushes an immutable commit-tagged image.
- [ ] GitHub Actions deploys the image with Helm.
- [ ] Rollout verification passes.
- [ ] Smoke test validates health and deployed version.
- [ ] No long-lived AWS keys are stored in the repo/workflow configuration.
- [ ] Teardown path is documented and tested.
- [ ] Architecture/tradeoffs are documented.
- [ ] Evidence suitable for GitHub/CV/video exists.

Only then create release/tag `v0.1.0` and move active implementation focus to v0.2.

## Suggested portfolio story

> Built a reproducible Amazon EKS application platform using Terraform, ECR, Helm and GitHub Actions. Implemented OIDC-based CI/CD authentication, immutable image releases, Kubernetes health/resource controls and automated deployment verification as the foundation for an observable AgentOps platform.

This becomes the baseline evidence that later AI-agent claims are running on real platform engineering rather than a local notebook demo.
