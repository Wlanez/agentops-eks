# v0.2 Observable

## Goal
Make the platform diagnosable before introducing AI reasoning.

## Entry requirements
- v0.1.0 Definition of Done satisfied.
- Stable demo deployment through GitHub Actions.
- Reproducible EKS environment.

## Required capabilities
- OpenTelemetry Collector deployed in Kubernetes.
- FastAPI traces and application metrics.
- Centralized application logs.
- Kubernetes metrics/events needed for incident analysis.
- Request/trace/log correlation where practical.
- Dashboard for latency, traffic, errors and saturation/restarts.
- At least one actionable alert.
- Telemetry backend selected and documented; OpenTelemetry config remains portable where practical.
- Telemetry components have resource requests/limits.

## Required scenarios
Implement at least one repeatable fault such as latency spike or controlled application error and demonstrate that telemetry shows:

1. when the problem began,
2. which service/workload is affected,
3. relevant metrics,
4. relevant logs,
5. a trace or request path where applicable.

## Definition of Done
- [ ] Collector is deployed from code/Helm/manifests in Git.
- [ ] Application emits traces.
- [ ] Application/platform metrics are queryable.
- [ ] Application logs are centralized/queryable.
- [ ] Dashboard shows the agreed golden signals.
- [ ] Alert fires for a reproducible scenario.
- [ ] A developer can correlate enough telemetry to explain the scenario.
- [ ] No AI agent is required to diagnose the incident.
- [ ] Architecture/evidence is documented.

## Out of scope
- Autonomous remediation.
- Kubernetes write permissions for AI.
- Human approval workflow.

## Portfolio evidence
Show a failure being introduced, detected and explained through metrics/logs/traces. This is the evidence foundation for v0.3.
